# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Cronus is a custom cron daemon. Its main feature: it runs "skipped" jobs. A skipped job is a job whose time came while the machine was off. Cronus runs such a job as soon as the service starts again.

The code is in three modules:

- `cronus.py`: the daemon (`Task`, the status stores, `Crontab`, `Tasks`, `Cronus`, the `Watchdog`, `main()`).
- `file_watcher.py`: `FileWatcher`, `PollingWatcher`, `EventWatcher`.
- `instance_lock.py`: `InstanceLock`, `FlockLock`.

A family gets its own module only if it does not depend on `cronus.py`: an import back would make a cycle. The status stores work on `Task` and `Status`, so they stay in `cronus.py`.

Run it with a crontab file as the only argument:

```
python cronus.py [--watcher event|polling] /path/to/crontab
```

`--watcher` chooses the `FileWatcher`: `event` (needs `pip install watchdog`) or `polling`.

## Crontab format

Each line is `mon dom dow h m s command`. The six time fields accept `*`, `*/N`, `N`, `N-M`, and comma lists. In `dow`, 7 and 0 both mean Sunday. A line that starts with `#` is a comment.

The last calls are the persistent state that lets Cronus detect skipped jobs after a reboot. A `StatusStore` keeps them, chosen by one argument of `Crontab` in `main()`:

- `CrontabStore`: Cronus writes back to the crontab file. It appends ` #<called_at> | <alive_at>` to each task line. Each time is a Unix timestamp or `YYYY-MM-DD HH:MM:SS`, and Cronus keeps the format that the line already has. Everything is in one file, but Cronus writes the file that the user edits.
- `StateFileStore`: a separate JSON file, `<crontab>.state`, holds `[line, called_at, alive_at]` entries, keyed by the task line without its suffix. Cronus never writes the crontab. A suffix already in a line is used only until the state file has that line.

## Tests

The tests use `unittest`. Run them from the `tests/` directory, with the repository root on `PYTHONPATH`. The tests open `__sandbox/...` with relative paths, and they import `cronus` and `unittest_data_provider` from the root.

```
cd tests
PYTHONPATH=.. python -m unittest test_task                     # fast unit tests for Task
PYTHONPATH=.. python -m unittest test_task.TestTask.<method>   # one test
PYTHONPATH=.. python -m unittest test_cronus                   # slow functional test
PYTHONPATH=.. python -m unittest test_robustness               # lock, watchers, watchdog, shutdown (slow)
```

`test_robustness` uses real time and a temporary directory per test, not `__sandbox`. It runs Cronus in a thread with a `StoppableClock`, or as a real `python cronus.py` process when it needs signals (SIGTERM, SIGKILL). Its long tasks run once a year with a last call of `#0`: each runs at once as skipped, and Cronus has no later events, so it never saves on its own during a test. The tests of a save or a wake-up use a `ManualClock`, which stands still until the test moves it. The test opens a gap (a half-written or missing crontab), keeps it open, and moves the clock: to the next minute to make Cronus run a minutely task and then save, or more than the wake-up interval ahead to make it wake up. The save tests set a file check interval longer than the test, so only the save can see the gap. `TestRobustnessWithEvents` runs the same tests with `EventWatcher`, whose settle interval is the test's check interval. A real process gets the same watcher through `--watcher` (`watcher_option`), so no test is skipped; the whole class is skipped only if the `watchdog` package is not installed. `tearDown` stops a real process with SIGTERM, so Cronus stops its tasks itself, then waits until each task's process group is gone: on macOS, `killpg` fails with `EPERM` while only zombies are left, until they are reaped. A group still running after that is killed, and the test fails.

`test_cronus` runs the real daemon in a thread. A `MockClock` reads the fake current time from `tests/__sandbox/time.txt`. Tasks in `__sandbox/crontab_begin` append to `__sandbox/sandbox`, and the test compares that output with the expected events. The test edits `crontab_begin` during the run and restores it at the end. At the end it compares the result with `crontab_end`. The test uses fixed `time.sleep` delays for each OS, so it is timing-sensitive.

`unittest_data_provider/` is a vendored copy of a small data-provider decorator for tests.

## Architecture

- `Task` parses one crontab line with the regex at the top of the file. It expands each field to a sorted list of values. `calls(from, to)` lists the run times in a window. `__expected_last_call()` searches backward for the most recent scheduled time. `is_skipped()` compares that time with the stored last call. `execute()` starts the command with `Popen(shell=True)` in its own session, so the shell leads a process group that holds everything the command starts. It does not start the command again while the previous process is alive. Instead it refreshes `alive_at`. `execute()` returns whether it called the command. `Task.stop(tasks, timeout)` stops the groups of many tasks at once with `stop_groups`: SIGTERM, then SIGKILL to the groups still alive after the timeout, so it takes at most about the timeout in total. The timeout is `Tasks.__stop_timeout`; `__del__` stops one task the same way, with its own timeout. A process that leaves its group (`setsid`, daemonizing) is not reached.
- `Crontab` is the crontab file: all access to it goes through it, and `Cronus` never touches the file or its path. It holds the path and what is bound to it: its `FileWatcher`, `StatusStore` and `InstanceLock`, all private. It takes a factory for each (a class, or a lambda for other arguments) and makes each from the path, so they cannot be given different files. It reads the file (`read()`, `is_changed_from(lines)`), forwards the watcher's sleep and `is_saved()`, waits for a saved file (`wait_until_saved()`), and forwards the store's `merge`, `restore` and `save`; its `save` calls the watcher's `reread_later()` when the store did not save. `str(crontab)` is the path, for alerts. `Cronus(crontab, clock)` takes it; the clock, the watchdog and the timeouts are not bound to the file, so they stay in `Cronus`. `run()` enters the crontab in its `with` block: it enters the lock first, so a second instance never starts watching, then the watcher, and exits them in reverse. `StateFileStore` takes the crontab's path too, and adds `.state` itself.
- `Tasks` is the crontab's tasks by line index, with the lines last read or saved, and their processes; `Cronus` makes it from its `Crontab`. `read(now)` re-reads the crontab and reconciles the tasks, `save()` saves their statuses, `is_crontab_changed()` compares the file with the lines, `skipped(now)` lists the skipped tasks, and `execute(tasks, now)` runs tasks and returns whether any command was called. It owns the `Watchdog` and keeps it in sync, and its `__exit__` stops all tasks. `Cronus` keeps the time: the clock, the event queue, the sleep, the wake-up, and when to save.
- `Cronus.run()` is the main loop. It reads the file and runs skipped tasks. Then it builds a one-day queue of `Event`s (a time plus the tasks due at that time), sleeps until each event, and executes its tasks. If Cronus is late, but by less than a wake-up, for example after a short system sleep, `__next_tasks()` merges all events due by now, so each task runs once, as a skipped one, not once per missed event.
- Control flow uses exceptions. `FileChangedException` comes only from `__sleep()`, when the watcher reports a change and the contents differ from the lines last read. `WakeUpException` comes when the clock jumps more than `__wakeup_interval_seconds` past the expected time, for example after sleep or suspend. Both restart the loop and cause a full re-read. After a wake-up, `Crontab.wait_until_saved()` first waits until `FileWatcher.is_saved()`: the file exists and stays unchanged for the settle interval, because an editor may be in the middle of a save. It waits as long as it takes, and alerts once after its settle timeout.
- On re-read, `Tasks` maps tasks by line index. If a line is unchanged, it keeps the old `Task` object, so the running process and the last call survive. Otherwise it creates a new `Task`.
- Cronus writes last calls back to the file at most every `__saving_interval` after a call, and at most every `__alive_saving_interval`, a longer one, when only `alive_at` changed, that is, a task's process was still running at its call. `__execute()` tracks this in `__called_since_save`. The longer interval keeps a long-running process scheduled every second from causing a save after every call. The cost: after a reboot, `alive_at` may be up to that interval old, so a call dropped within it runs as skipped at start. Cronus also writes when `run()` ends, which then stops the processes of all tasks. The write is atomic: a temp file next to the real path (symlinks are resolved), synced (`F_FULLFSYNC` on macOS, `fsync` elsewhere), then `os.replace`. The temp file gets the crontab's mode, and its owner and group when Cronus may set them (as root). This needs write access to the crontab's directory, and it breaks hard links.
- `Cronus` has no `__del__`. `run()` enters the crontab and then the `Tasks` in a `with` block, and calls `__save()` in `finally`; then `Tasks.__exit__` stops all tasks at once, so the save always comes first. This happens on any exit, including `SystemExit` and `KeyboardInterrupt`. In `main()`, a handler for `SIGTERM` and `SIGHUP` (the terminal is closed) raises `SystemExit`, so `kill` also saves the status and stops the tasks. A signal that is already ignored, such as `SIGHUP` under `nohup`, stays ignored. The handler restores the default for both signals, so a second one exits at once without cleanup, and the watchdog stops the tasks.
- Only one instance may run per crontab file. Instances for different crontabs may run side by side. An `InstanceLock` enforces this, chosen by one argument of `Crontab` in `main()`. `Crontab` enters it, and its `__enter__` fails if another instance holds it. `FlockLock` takes an `flock` on `<real path of crontab>.lock` and fails if another process holds it. The lock is on a separate file because each write replaces the crontab's inode. On exit, Cronus deletes the lock file while it still holds the lock, and only if the path still names its own file. On start, after `flock`, it checks that the path still names the file it locked, and retries if not. Together, this stops two instances from locking different inodes. Only a hard kill leaves the file behind. That is harmless: the next instance reuses it.
- A `FileWatcher` tells Cronus when to re-read the crontab, chosen by `--watcher` in `main()`. `sleep_until_changed(seconds)` sleeps, or returns `True` earlier once the file changed and looks saved; `__sleep()` calls it for at most `sleep_interval_seconds`, then reads the clock again, and compares the contents, so Cronus's own writes are not reported as the user's. `reread_later()` makes the next sleep report the file even with no new change. `is_saved()` (in the base class) checks that the file exists and stays unchanged for the watcher's settle interval. A missing file is not an error: an editor that saves by rename brings it back later, and `Crontab.is_changed_from()` calls `reread_later()` for it.
- `PollingWatcher` needs nothing from outside. Every check interval (real time) it runs `os.stat`. It reports a change when the inode, size or mtime changed and stayed the same for one more check, because a writer may be between the truncate and the write. It also reports when the last report was shortly after the mtime, because a coarse mtime can hide a second write in the same tick. Its settle interval is the check interval.
- `EventWatcher` uses the `watchdog` package from pip (inotify on Linux, FSEvents on macOS), imported only in its `__enter__`, so `--watcher polling` needs no package. `Crontab` enters the watcher. It watches the crontab's directory, because a save by rename replaces the file, and matches the real path of each event's `src_path` and `dest_path`. The observer's thread records the time of the last event; a sleep reports it once no event came for the settle interval. A change still settling when a sleep ends stays pending for the next sleep, so a busy file never delays an event.
- On re-read, `Tasks.read()` calls `Task.stop` on old tasks that no longer match any line, so their processes stop at once. It does not rely on GC, because PyPy has no reference counting. GC may call `__del__` later, which does nothing once the process is gone.
- The `Watchdog` class covers a Cronus that dies without cleanup, for example by `kill -9`. `Tasks` enters it in its own `__enter__`, which starts `python cronus.py --watchdog <stop timeout>` in its own session, with a pipe on its stdin; `Watchdog.serve()` is that process's side. `Watchdog.sync(pgids)` sends `+<pgid>` for each new running task and `-<pgid>` for each ended one; `Tasks.sync_watchdog()` calls it after tasks run, after each re-read, and after each `sleep_until_changed()`, that is, at least every `sleep_interval_seconds`, so the pgid of an ended task, which the OS may reuse, does not stay registered until the next event. When Cronus exits for any reason, the OS closes the pipe; on EOF the watchdog stops the groups still registered and exits. It ignores SIGTERM, SIGINT and SIGHUP, so it only ever stops after Cronus.
- The stores: `StatusStore.merge(task, read)` runs on re-read for a kept task, `restore(tasks)` for new ones, and `save(tasks, lines)` returns the crontab's lines after the save, or `None` if not saved. Both stores write with the module-level `write_atomically()`. `CrontabStore.merge` keeps the newer times (`Status.merge`), and its `save` passes a check to `write_atomically` that the crontab still matches the lines last read. `StateFileStore.merge` does nothing, because the status in memory is the newest; its `restore` takes entries for identical lines in order, and its `save` always succeeds and leaves the lines as they are.
- Cronus never overwrites the user's edits. Before the `os.replace`, after the slow sync, `CrontabStore` checks that the file still matches the lines it last read. If the file changed or is missing, `save` returns `None`, and `__write()` writes nothing and returns `False`. It does not re-read the file itself, because it might catch it half-written or in the middle of a save by rename. Instead `Crontab.save()` calls `reread_later()`, so the watcher reports the file once it looks saved. On exit no watcher runs, so `__save()` retries for up to `__save_timeout`: it re-reads only once `is_saved()`, and alerts if never. On re-read, `Status.merge` keeps the newer value of `called_at` and of `alive_at` separately, and drops an `alive_at` older than the merged `called_at`. The format always comes from the file. Right after each re-read, `run()` calls `__write()`. That rewrites a line only if one of its saved times is older than the one in memory, so a stale save is corrected at once and any other line stays as the user saved it. The exception is a new line without a status: it gets one at once, so the file changes right after the user's save, and an editor may say it changed on disk. Cronus tells its own writes from the user's by comparing contents, not by timing.
- All time comes from an injected `Clock`, and only `Cronus` holds it. `Task` and `Tasks` get "now" as an argument (`from_string`, `execute`, `is_skipped`, `read`, `skipped`), so the tests give them any time directly. Do not call `datetime.now()` directly in the daemon, because the tests mock time through `Clock`.
